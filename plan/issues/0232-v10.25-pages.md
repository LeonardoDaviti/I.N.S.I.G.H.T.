# 0232: Pages: capped limits, one kept page an entity, News never built in a request, pages kept across a deploy (Stealth v10.25)

Status: **built** on slice G's branch (backlog 0225 #12, #13, #14, #23, #24, and 0216 item 5). Migration 0162. Module
tests only. **Not measured after the change on real data**: the scratch Postgres was recreated at 13:15 UTC on
2026-11-19 (every clone and template gone), and then the owner ordered no testing on real data and no requests to the
server. The before numbers below were taken on a clone of `v1024srv_s1` before that.

## What was wrong

- **#13 / #23, the limits.** `GET /api/markx/entities/{id}` took `stories_limit`, `loose_limit` and `by_limit` up to
  100000, and every combination of limits was its own kept key. A page asked with its own limits was built in the
  request. The worst case built the whole page: on the clone, the largest entity (32,820 current mentions, the
  Qwen-shaped one) at 100000/100000/100000 took 10.4 s and made a 15.5 MB answer, with the measuring process at a
  658 MB peak (191 MB at the default limits).
- **#12, News.** `news.kept_page` returned None as soon as any input moved (a label, a headline answered, a new run).
  Then the route built News in the request: 11 s on the server.
- **#24, deploys.** The code stamp was hashed into every input stamp, so a deploy made every kept page cold.
  Also, the first decision run after a deploy is a long full one, and the kept views are built only after it.
- **#14, cold pages.** The cold build of the largest page took 6.3 s on the clone, 4.2 s of it SQL. The two biggest
  queries were `entity_views._rows` (0.62–0.65 s) and `timeline.lines_of` (0.56–0.75 s). Both did a **sequential
  scan of all of mx_mentions** (1.55M rows, 87k buffers) for any entity, even one with five posts. The cause:
  `entity_id = ANY(ids) OR (post_id, guide, n) IN (pins)`, an OR the entity index can't serve.
  In the Python profile, `timeline.of_entity` took 3.0 s of the 6.3 s (slice I's module: `from_maker` / `_site`
  URL parsing 1.0 s). `news._posts` took 1.1 s: it computes bylines for all 34k posts, though the page lists about 1k.
- **0216 item 5.** The entity list (4 s on the server) and the queue's first page (2.7 s) were built on every open.

## What changed

- **`kept_pages` (the owning module).**
  - Migration 0162 adds `mx_kept_pages.code`. The stamp now covers the inputs only, and the row records the code that
    built it. `get` and `has` want the current code's row.
  - `get(..., any_code=True)` also sends a row built by the previous code, but only while the inputs are the same. A
    page that opts in names its answer's shape in its key (`shaped`), so a row of another shape is never sent, by
    `get` or by `newest`.
  - `recut` reads kept bytes back, changes them and renders them the way the route does.
  - `opened` / `most_opened` count opens in the new table `mx_page_opens`.
  - Callers that don't opt in (tracks, unread, Discover, anatomy) behave as before.
- **Entity pages (`entity_views`).**
  - `limits()` clamps each limit into its range: stories 1..200, loose 1..500, by 0..500. Out-of-range values clamp
    instead of returning 422.
  - Each entity keeps one page per `replies`, built at the caps (`_full`). Every request is cut from it (`_cut`), byte
    for byte the page built at those limits (tested).
  - The open is counted.
  - `_rows` reads the linked mentions through the entity index and the pinned ones separately (a UNION ALL). On the
    clone the largest entity's query went 645 ms → 136 ms (EXPLAIN ANALYZE). Smaller entities skip the full scan;
    not timed.
  - Outside my files: I made the same minimal rewrite in `timeline.lines_of` (slice I's file).
- **News (`news.kept_page`).** It sends the view kept for the inputs now, else the newest kept view while the jobs
  process builds the next one. News is built in a request only when no view of this shape was ever kept (the first
  start).
- **The list and the queue (0216 item 5).** Both are kept pages, built by the jobs process and sent by the routes
  through `kept_or_build`.
  - Their strict inputs: the run, the owner's marks, the mention sets, and the queue's counts, times and flag notes.
  - The list may lag its posts' titles and read flags, its "N days ago" text and its window's edge by at most
    `KEPT_LAG` (15 min).
  - Queue pages other than the first flagged one are built live, as before.
- **The jobs process (`jobs.py`).**
  - A new kept view, `entities` (migration 0162 adds it to `mx_jobs_job_check`). It builds the list, the queue's
    first page, and the 20 most-opened entity pages (opened in the last 14 days, at most 120 s a build). It runs after
    every decision run, and the list and queue also whenever their inputs change (at most once a minute).
  - `KeptView.after_deploy` (News, entities): the runner's first look after `start()` (a deploy or a restart) builds
    these before any other job, ahead of the long full decision run.
  - Until then, pages whose inputs haven't changed are sent from the previous code's rows.

## Is serving an old-code page safe?

- **News, the list, the queue, an entity's page.** Yes, while the inputs and the shape are the same.
  - Each page's shape (`news.SHAPE`, `entity_views.PAGE_SHAPE`, `LIST_SHAPE`, `QUEUE_SHAPE`) is in its key.
  - `test_markx_kept_pages.TheShapesAreNamed` freezes a digest of each page's key paths on the test world. A change to
    what a page answers fails that test until the SHAPE is bumped.
  - What remains: a deploy that fixes a wrong value without changing the shape shows the old value until the jobs
    process rebuilds the page, which happens at the runner's first look.
- **Not opted in:**
  - Tracks, unread counts, source anatomy and the Discover main-source list need the current code, as before.
  - The Discover list's key already names the code.
  - Their answers come from code that changes often, and nothing checks their shape.

## Left

- `timeline.of_entity` (3.0 s of the largest page's cold build, slice I's module) and `news._posts` (bylines for every
  post of the page) are the next costs of a cold page. Neither is changed here.
- The hot pages go missing only on a new run or code. A page an owner's mark made stale between runs is built at its
  next open, as before.
- The jobs process's builds of opened pages also make those pages' sample offers, as an open would.
