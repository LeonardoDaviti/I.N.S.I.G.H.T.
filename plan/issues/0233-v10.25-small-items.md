## #6 Back in the news is shown though its feature is off
**Wrong.** 0210 switched the feature off (`markx/consumers.py` `back`: its bar failed, 68%; the owner's labels 4/11) and
stopped its questions, but `back.page` still served every row and the News tab still rendered the section below Mark X
News (v10.24 moved it there).
**Changed.** The switch now decides what is shown, in the module that serves it: `back.page` reads the feature's state
and, off, returns `{on: false, items: [], counts: {}, precision: null}` without reading a row. `MarkXBack` renders
nothing when `on` is false. The rows, tasks and labels stay (keep everything); switched on again on /markx, the same
rows come back. Tests: `test_markx_back.TheQuestions.test_off_is_not_shown`, `back.test.tsx`.

## #17 The "last posts" planner asks old kinds with ent-v5 on
**Wrong.** `tasks.plan_last_posts` (0132 C1, behind `INSIGHT_MARKX_READ_LAST20`) was wrapped around the `read` and
`entities` planners only and never asked which reading is current: with ent-v5 on, a thin source's last posts got
`read` and `entities` tasks, the kinds ent-v5 replaces (`reading5.OLD_KINDS`).
**Changed.** The planner asks only the current reading's kinds: with ent-v5 on (`reading5.is_on`) `read` and
`entities` plan nothing there and `reading` (now wrapped too) asks the last posts that no guide the pickers read
(`reading5.guides`) has read yet, through `reading5.add_posts`, the one place a post's reading is asked (the fresh
lane's loop, moved out of `reading5.plan`). Off or in Shadow, as before. Test:
`test_markx_sources.Stance.test_last_posts_ask_only_the_current_readings_kind`.

## #18 Ghost process entries in monitoring
**Cause.** The API supervisor wrote a beat per live API process (`api-<pid>`, 0216) but nothing ended a beat when its
process ended; the reader (`heartbeat.processes`) deleted an API beat only an hour (API_GONE) after its last write. So
`/api/status` `checks.processes` listed for up to an hour: a worker the open-files guard killed and uvicorn replaced,
every API process of the previous container after a restart or deploy (new pids, same logs volume), and uvicorn's own
pid, beaten while it ran alone before its workers were up. (GET /metrics hid beats older than 120 s, so Grafana's
series stopped, but the status page did not.)
**Changed.** The writer owns the end: `beat_api_processes` writes the live processes' beats and removes every other
`api-` beat in the same step (`heartbeat.only`). The reader no longer deletes files and API_GONE is gone. The
scheduler's and Mark X's loop beats are untouched (not the supervisor's). Test:
`test_metrics_0216.TheBeatsCarryTheNumbers.test_an_ended_api_process_is_listed_no_more`.
