## A. A deploy that finishes by itself
1. **Background work never stalls** (rehearsal, run 3). The search refill and link reading skip each other's locked rows, and each stops at its first empty batch, so 311 posts stayed un-indexed and 11 posts' links unread until a restart.
   - Decided: each keeps going while posts are pending, after a short wait when a batch came back empty because of locked rows. It stops only when none are pending.
   - Done when: a test with two workers over the same rows leaves 0 pending.
2. **Downtime is the API's start, not a 30-second wait.** `up -d` starts the frontend only once the backend is healthy, and the first health check runs 30 s after start.
   - Decided: the health check starts early and checks often (`start_period`/`interval`), so the frontend starts once `/health` answers (about 5 s).
   - Done when: the downtime is measured again with the compose file, on local images only.
3. **npm packages aren't reinstalled on every deploy.** In `frontend/Dockerfile` the build stamp's ARG/ENV come before `RUN npm ci`, so each commit invalidates that layer.
   - Decided: the ARG/ENV go after `npm ci`.
   - Done when: the Dockerfile is checked by reading the layer order. Don't build it here, because a build would run `npm ci` and download.
4. **A rule change reaches old stories** (R2). 0068 changed voices and titles without forcing a full regroup, so 1,574 of 1,796 lab stories kept old voices and titles.
   - Decided: the stories setting records a rules version. When the code's version differs, the next run is full. Bump it in this issue.
   - Done when: a test that a version change makes the run full.

## B. Text that reads
1. **No dead ends** (R1). A post with no body shows its excerpt, or its title when there's no excerpt, and "Read on <site> ↗", never "No content available".
   - `repair_full_text` records its attempts, so 0062's retry covers those posts later.
   - The owner runs the repair after the deploy; this build fetches nothing.
2. **No holes, no broken lines** (R3). `whitespace-pre-wrap` stays only for bodies stored as plain text, not for HTML bodies (`MarkdownRenderer.tsx`).
   - Done when: screens of an X post, a thread reply and a Daring Fireball post, before and after.
   - The page corpus (0032/0053) is no worse.
3. **Titles say what the post is** (R5).
   - A placeholder title (`[Photo]`, `[Video]`, `[Media]`, `Image`, `R to @…:`, a bare address) counts as empty, so the text's first sentence is the title.
   - Placeholders are recognized by shape (bracketed media words, a reply prefix, an address), with no list of phrases per site.
   - A first line that ends without finishing a sentence (`Day 25/`) continues to the sentence's end, within the title's length.
   - Done when: Tibo's "Day 25/" and `t.me/seeallochnaya/4011` read right in News and the feed. Record how many titles change on the lab, with 30 checked by hand.
4. **Telegram albums are one post** (R4). Media-only posts of one channel within 2 minutes after its previous post are that post's pictures.
   - Measure first: 2,188 on the lab. Check 30 by hand.
   - They fold into the post before them, shown in its body, not as rows. Their read state follows that post.
   - No data is deleted.
5. **One count everywhere** (R6). News, the feed row and the post page show the same number: the story's voices.
   - News never reads "1 source · 1 share": a share is a source.
   - Gemini 4 Carbon reads the same in all three places.

### A1. Background work never stalls
- `db.fill_until_done` (database.py): a fill runs a batch a transaction until its `pending` check finds nothing left. A batch that comes back empty while posts are pending found only rows another worker holds (`FOR UPDATE SKIP LOCKED`): it waits `LOCKED_WAIT_SECONDS` (1 s) and goes on. With nothing pending it stops at once, as before.
- The search refill (`ReaderService.fill_search_vectors`, pending: `SearchRepository.missing_vectors`) and the link reading (`StoriesService.fill_links`, pending: `StoriesRepository.missing_links`) both use it. The pending checks count locked rows too: a plain `EXISTS`, read only when a batch was empty.
- **Tests** (`test_deploy_finishes.py`, `FillsFinishTests`): while a second connection holds every pending post, a batch finds 0 (the case that stopped the refill), the fill is still running after 0.5 s, and it finishes once they are let go, leaving 0 pending, for each fill; both fills started together over the same rows leave 0 and 0; with nothing pending a fill returns in under a second.
