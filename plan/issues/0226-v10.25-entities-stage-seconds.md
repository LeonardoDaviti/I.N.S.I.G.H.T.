## Why the linking did 1 part of 13

A part starts only if the seconds the last part took are still left. The first part also decides the answered pairs
and the backlog and asks their questions, once a run. Leaving out the reading and the facts, it took ~22 s on the
clone, so the next part was expected to take ~22 s plus its collisions. That never fitted, and the 5.5k mentions
waited, run after run. On the server the first part alone took the whole budget (44-54 s; 114 s at 12:28 with
11,457 answered pairs).

## What changed

- **A part is expected to take a plain part's seconds** (identity.stage `part_took`). A plain part is one that
  decided only its own mentions' pairs, so the first part counts only when it carried no answered pairs and no
  backlog. The value is this run's last plain part, else the last run's (`incremental.part_took`, passed on by
  entity_stage), else PART_GUESS (5 s). The decisions are unchanged: the same pairs, in the same parts, in the same
  order. Only how many parts start changes.
- **The decisions' alias items are read in one go** (`identity.queue_state`, one statement a chunk). An item is
  closed or refreshed only where its pair has one open, and a new item skips its own read
  (`queue_item(held=...)`). Before, every pair kept apart cost a savepoint and an UPDATE (the server: 2.6k-15.5k a
  run), and every queued pair cost a SELECT plus a savepoint UPDATE. The rows written are the same.
- **The counts say where the linking's seconds go** (#29): `incremental.timing` (the linking's steps: load, link,
  facts, paren, pool, pairs, vectors, answers, decide, decide.rules (inside decide), ask, write.<tier>, collide),
  `reading` (the pool's indexes, inside pool), `part_seconds`, `pairs`. The stage's `timing` gets the same keys.
- **The graph stage's counts say each step's seconds** (`graph.timing`: links, backfill, next_version, relations,
  relations_backfill, discover, relate_backfill, verdicts, plan) and `relations.scope` (since_posts, merged_posts and
  each read's seconds: #16). This is a small edit in `graph.stage`, outside _relation_scope, to find the 430-514 s.

## Not built, and why

- **#10, the pool's indexes stored**: measured at 12.2 s cold on the clone (server 11.5-13.1 s), all of it CPU. Not
  built. The only by-need design that removes the CPU is a gram table, about 4-5M rows and 200-400 MB with its index.
  It is read at random per chunk on a server whose reads are already disk-bound (#11), so it could be slower than
  the CPU it replaces. Whether it is can't be told without measuring on a cold clone. A design that keeps today's
  tie order exactly: read each gram's live ids ordered by `pg_temp.mx_run_order.ord`, the run's fresh entities
  appended as `_grow` does, `LIMIT GRAM_CAP` per gram for the cap. Then S1 would not change.
- **#11, nearest-name reads**: not reached. The full pass ran 0 chunks on the server and on the clone, so this run
  had no nearest-name read to measure. Candidates once it is measurable: a halfvec HNSW index (half the size: 886 MB
  -> ~450 MB, against shared buffers of 1.5 GB), or ef_search. Both change which neighbours are found at the margin,
  so they need an S1 measure.
- **#16**: instrumented only (`relations.scope`). Not measured at server size. Unverified: the first scope query's
  `EXISTS (... x.evidence->'posts' ? m.post_id)` tests each mention row since against the current stated edges, so
  its cost grows with mentions x edges. Read the counts before changing it.
- The ask's 3 statements a question (decide.Ask -> repo.add_task) are slice B's and repo's, not changed here.

## Risks

- The new expectation can let more parts start than the time left holds, when a plain part on the server takes
  longer than the last one measured (more family pairs). The first run after the deploy uses PART_GUESS (5 s).
- How much `queue_state` saves on the server is unmeasured. The statements removed are counted in the code, not
  timed.
