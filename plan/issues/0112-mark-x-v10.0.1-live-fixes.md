# 0112 — Mark X v10.0.1 (Shadow): readings the server accepts, checks that see the story, copies never checked, guides loaded safely

Status: **spec** (2026-11-05). This comes from the first real-Haiku runs of v10.0:
- live on the server, through the worker on the owner's device;
- on two scratch copies of the server's data, where Opus judged the results blind.

The private notes are `plan/research/lab/checks/markx-real-haiku-2026-11-05.md` and `markx-live-2026-11-05/`. Not built.

**Constraints:**
- download nothing;
- no real names in committed files;
- nothing merges unless `scripts/realdata-check.sh` passes;
- Mark IX's tables never change because of Mark X;
- keep everything: Mark X rows written under the bugs are closed (`valid_to`), never deleted.

## What v10.0 does wrong (measured 2026-11-05)

**1. Most readings with a mention are refused.**
- `read-v2.md` describes `mentions` but never names their field.
- The schema requires `{"name", "role"}`, and Haiku writes `{"event", "role"}` or similar.
- **The scale:**
  - about 45% of answer items are invalid (`answer.mentions[i]: name missing`);
  - on the two copies the server refused 1,692 and 3,440 items, after the worker's own retry;
  - 3.6–5.2% of posts end up with no reading at all.
- A post with no reading is never joined, paired or counted.
- **Live on the server:** 39 read tasks are `failed` after using their tries under this bug.

**2. A check can show Haiku an empty story.**
- `tasks.check_questions` shows the story as its `report` members minus the checked post.
- When the checked post is the story's only report, Haiku sees `STORY / Headline: (empty)` with no members. It answers "can't tell" or "different", and the post is removed.
- This happened in 10 of 185 and 21 of 399 check inputs (about 5%).
- Example: a post on research teaching a fly's brain to play a VR game was removed with the reason *"no relation to the empty story"*. It was the same story as another source's post on the same day.
- `decide.plan_pass1`'s `shown` has the same gap.

**3. Identical reposts are checked, and removed.**
- 9 of 44 removals were members whose text is identical to another member's (ratio 1.00).
- In each, the story was shown correctly and Haiku answered "different" at 0.10.
- Example: two channels' identical one-line teaser posts, both removed in the same story.
- Overall, removals and demotions were right in only **14 of 44** (32%, 20–47%), by a blind Opus judge.

**4. Guides load with a race, and the first parallel leases fail.**
- `schemas.ensure_guides` marks a database's guides loaded (`_ready.add`) before the transaction that loaded them commits.
- So a second thread can insert `mx_tasks` naming a guide that isn't committed yet: a foreign-key failure, HTTP 500 to the worker (exit 3).
- It happens on a fresh database, or after any guide change, when several workers lease at once. Two workers exited this way on the copies.

## Decided
1. **The worker sends each guide's answer schema with its body:** `system_for(guide)` is the body plus "Each answer object (after its id) must match this JSON Schema, with exactly these field names:" and the compact schema.
   - This fixes every task kind whose prose leaves a key unnamed, without changing a guide's body, sha256 or id.
   - Already measured live on the server: **39 of 39 readings valid, 0 refused**; one call took 14 s, against 44 s before.
   - It's on the local branch `markx-v10.0.1` (10984d9, not pushed), and is also uncommitted in the main checkout because the live worker uses it.
   - **Not done here:** a `read-v3` that names the field in its prose. That comes with Stealth's event types, as a new guide id.
2. **A check never shows an empty story:**
   - when the report members minus the checked post are none, it shows the story's other members (any role) and its card;
   - when there are none either, no check is asked: a story's only post is never checked.
   - This applies to the same rendering in `tasks.check_questions` and `decide.plan_pass1`.
3. **A near-copy of another member is never checked:** the same source or not, the same folded text, or a 5-word shingle Jaccard ≥ 0.6. It can't be removed or demoted by a check. It stays a member and counts once as a voice, by its source. This is the prototype's measured rule (0106 step 1).
4. **`ensure_guides` marks a database ready only after its loading transaction commits.**
   - Concurrent first leases wait on the lock and then see committed guides.
   - A failed load leaves the database not ready, so the next caller retries.
5. **Read tasks that failed only from bug 1 are reopened once, on deploy:** `failed` read tasks whose every recorded error is `answer.mentions[i]: name missing`.
   - Done by the codebase's one-off repair path (a migration, as 0067 re-read stored links).
   - Their failed answers stay recorded; nothing is deleted.
6. **Removals made under bugs 2 and 3 are re-decided, not trusted.**
   - The next decision run after deploy re-asks the checks whose input showed an empty story, or whose member is a near-copy.
   - It closes those removals (`valid_to`) where the new answer keeps the post.
7. **The version is "Mark X v10.0.1 (Shadow)".**
9. **The reading window is the owner's to change at any time, from the page or from the worker** (owner, 2026-11-05: "run on 120 days"; "settings to change that anytime … I don't want the worker to be limited only with that setting, I should be able to run it anytime").
   - **The page setting:** the `/markx` Worker tab has "Reading window": 30 days, 120 days, everything, or a number of days.
     - Stored in the database (an `mx_settings` row), read by the `read`/`entities`/`embed` planners on every run, so a change counts from the next run. No `.env` edit, no deploy, no restart.
     - Default 30. The owner's server is set to 120 on deploy.
     - It replaces the constant `tasks.PLAN_DAYS` for those three planners.
   - **The worker's own window:** `markx-worker cycle … --days <N|all>`. A lease that carries `days` makes the server plan that kind's tasks for that window first, newest first and capped as today (`PLAN_LIMIT` a call), then hand them out.
     - So the owner can backfill any range from the device at any time, whatever the page setting.
     - Without `--days`, the page setting holds.
   - **What stays at 30 days:** the decision window (`decide.Config.days`) and `plan_checks`. Deciding older stories asks about 4× more judge questions, and waits for this release's fixes. It's a separate setting later.
   - **Why the constant existed:** the build plan's correction 8 ("the worker shares the owner's Claude usage with build agents"). The owner has since said Haiku has no usage limit.
   - **What it gives:** Mark X's memory, not its News. Entity lines across versions since July (0090) and back in the news (0092), plus chains across months (0091), numbers over time (0095) and questions with citations over the whole history (0098). Stealth can then be tested on live data.
   - **Cost, from the live calls after fix 1:** 120 days is about 15,000 posts, read and entities, about $9 of Haiku; everything (about 49,600) about $30.
   - **Tests:** the page setting changes the next planner run's window; `--days 120` plans older posts on lease; `--days all` covers every post; neither touches the decision window.
   - **Measured live (5 Nov):** about 100 parallel `claude -p` calls on the device made its Tailscale DNS stop resolving, twice. The DEPLOYMENT note says to start the worker at `--parallel 10` and raise it in steps.

## Not in v10.0.1 (next, before Part G)
- a check of whole groups after pair glue and merges, for the 40-, 25- and 17-post chains of several happenings;
- the shared-member rule: two stories that share members, judged the same happening, become one;
- `development` answers become "follows up" links, not membership. 18 of 80 sampled joins were wrong, mostly follow-ups or essays that use the event as their premise;
- merges and joins asked in small batches or alone. The prototype measured this at 59% → 89% for merges; the built v10.0 already reaches 93% (57 of 61);
- reproductions and first tests beyond 72 hours as candidates;
- a clock bound for replays: the job has no upper date bound, so a replay at an old clock decides up to today.

## How it's measured before merging
1. **Unit tests for each fix:**
   - the schema text in the worker's system prompt;
   - a one-report story's check input is not empty;
   - a near-copy is never a check question;
   - two threads leasing on a fresh database both succeed;
   - the reopen picks only bug-1 failures.
2. **`scripts/realdata-check.sh` on the server copy:** PASS, and Mark IX's derived tables unchanged.
3. **On a scratch copy of the server's data, with real Haiku, against v10.0 on the same copy:**
   - refused readings (was about 45% of items);
   - posts with no reading (was 3.6–5.2%);
   - checks with an empty story (was about 5%);
   - identical reposts removed (was 9);
   - removal and demotion precision by a blind Opus judge (was 14 of 44).
   - **Bar:** 0 refusals from bug 1, 0 empty-story checks, 0 near-copies checked, removal precision clearly above v10.0's. Shown as rows: right, wrong, missed.
4. **The deploy note (DEPLOYMENT.md):**
   - the worker on the device must be updated with the server, because the schema-in-prompt lives in `scripts/markx-worker`;
   - the reopened tasks are read by the next worker cycle.

## While v10.0 runs live
- The device worker already runs fix 1.
- To avoid writing wrong removals and merges, the live worker answers only: `embed`, `read`, `entities`, `join`, `pair`, `card`, `headline` and `connect`.
- `check` and `merge` tasks wait in the queue until v10.0.1 is deployed. On the copies, merges were right 57 of 61, but checks feed the removals measured above.
