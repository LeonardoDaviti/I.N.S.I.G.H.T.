## Part A: entities

### A1. Identity (0090 B–C), as 0090's design says
- **Name key and version parser in code (0090 B):**
  - NFKC, dashes, casefold, ё→е;
  - letter–digit split ("Qwen3.8" → "qwen 3.8");
  - versions compared as tuples ("4.10" ≠ "4.1");
  - size and build never taken for a version;
  - mixed-script words flagged.

  0090's gold sets become regression tests.
- **Tables (the next free migration number at merge (v10.0.2 uses 0070), Mark X only):**
  - `mx_entities`: id, type, name, parent (company → family → version → variant), maker, family key, version tuple, variant, status (provisional or confirmed), first seen;
  - `mx_entity_aliases`: key, entity, language, source (`rule`, `haiku`, `anchor`, `owner`);
  - `mx_entity_redirects`: from, to, when, by, and `undone_at`;
  - `mx_entity_queue`: the review queue. A pair, the system's proposal (same, other version or different), its confidence and evidence, and the owner's answer.
- **Linking** (a job stage after the entities' answers land: `entities_link`). **Incremental:** a run links only the mentions written since the last run (their `entities` calls), and the surges recount only the days those mentions fall on; a nightly full pass relinks everything and must match (as 0116 does for stories). After the 120-day reading there are mentions from about 15,000 posts: relinking them all every run is the kind of job that hung the API on 5 Nov.
  1. An exact key in the aliases links.
  2. A known family with a new version or variant creates a provisional child.
  3. An unknown family creates a provisional family.
  4. Each mention's `entity_id` is set at the most specific level the post states.
- **Uncertain pairs go to Haiku** (new task kind `alias`, below). Candidates:
  - the same family key with a different surface form;
  - embedding plus string similarity over names;
  - the maker-prefix forms ("deepseek_ai" / "DeepSeek");
  - "X (Y)" written inside one post.
- **Merging, conservatively (0090 C):**
  - **Automatic only when both hold:**
    - an anchor rule (the same official page or repository address, or "X (Y)" in one post), or Haiku says `same` at or above the confidence bar experiment 2 measures (**the bar is open until experiment 2's report**: `plan/research/lab/markx/proto/out/entity_identity/REPORT.md`; the auto-merge precision must be ≥ 95%);
    - **and** the pair parses to the same version and variant.
  - **Never automatically:**
    - across different parsed versions or variants;
    - a chain (one alias bridging two families);
    - a cluster above 10 aliases.
  - **Everything else goes to the review queue.**
  - **Until experiment 2 reports, and if it misses its bar,** the only automatic merges are identical keys and the anchor rules, and every Haiku `same` goes to the queue. The bar is applied only once it is written here.
  - **Every merge leaves a redirect** and can be undone from the queue's history.

### A2. Surges per exact version (0090 E)
- **A stage of the decision job:** `surges`, no model.
- **What counts:** per day, per entity at the version level, the distinct voices whose post has the entity as:
  - its subject;
  - the subject's maker or family (the roll-up);
  - or the actor.

  Measured 96% precise (81–99%).
- **When it surges:** 3 or more voices that day, and no 7-day warm-up (0090 E: it removed no false surge and 6 real ones). The 3× baseline waits for the first month of data.
- **Stored** as rows (entity, day, voices, posts, rule), with evidence: the posts.
- **Shown:** a "surging" mark on the entity list and on News rows whose subject surges.

### A3. The entity list and the entity page (0115, as decided there)
- **The list:**
  - one list, ranked like News: distinct voices over the window, then reports against mentions, then recency;
  - no Today/Week split;
  - each row: the name, type, maker and exact version; sources and posts counts; its Mark X stories; its 3 newest posts; "last seen";
  - read state never hides anything; read lines are dimmed.
- **The page,** `/markx/entities/<entity id>`:
  - every post in every role, the role shown on each line, grouped by its Mark X stories, ordered like News;
  - the posts in no story come last;
  - every source with its counts;
  - the family and its versions as links (GPT-6.1 Terra ↔ GPT-6.1 Sol ↔ GPT-5.6 Terra), and the family page lists every version.
- **The review queue,** a section of the Entities tab:
  - each item shows the two names, their posts (2 each), the proposal and its evidence;
  - buttons: **same / other version / different / not an entity**;
  - an answer applies at once (a merge, a split, or a redirect undone), and is also a label (`mx_labels` item kind `entity`). It is written by the API inside the request's own transaction (small writes to `mx_entity*` and `mx_labels` only); a decision run reads entities from its single snapshot (0112, v10.0.1), so an answer lands in the next run, never halfway through one.
- **The post page's Mark X panel** lists the post's entities; each opens its page.
- **Speed:** the list and the biggest entity's page load in under 1 s on the server copy (0115's measure).

## Part B: perspectives and the story sheet (0120 v3.2f)

### B1. Which stories
- Mark X stories with 3 or more voices in the News window. Each is re-judged only when its members changed since its last perspectives run, using the story's member set hash.

### B2. Inputs, built in code (a job stage: `perspectives_plan`)
Ported from `plan/research/lab/markx/proto/persp32.py`'s `Story` (the private lab, readable on the build machine), without its hardcoded maps:
- **Duplicates and near-copies are folded:**
  - same text;
  - same source with shingle Jaccard ≥ 0.6.

  They're shown as "N copies", never judged.
- **The original:**
  - by links: a member that is the page other members link;
  - the maker and the maker's link, from 0090's maker field and part A's identity, not from word lists;
  - page titles of repositories and model pages;
  - one original per page;
  - when no member is the original, the linked page itself is shown as "source page".
- **The hint "[the maker's own account or staff]"** comes from identity (a member's author is an entity whose maker is the story's subject maker). It's a hint for Haiku, never a label by itself (v3.2f).
- **Who wrote it:** the address, and "written by @x" for reposts and quotes.
- **The members are in published order;** each is judged against the original and the members before it.

### B3. New task kind `perspective` (guide `persp-v1`, from `persp_v32f_frozen.md`)
- **The guide:** the frozen v3.2f text, with its examples replaced by invented ones. Its md5 is recorded against the frozen lab file, so the port is checked as the same guide.
- **One call per story,** or per group of at most 5 members (`PER_CALL = 5`). Members a call skips are asked again alone, at most twice.
- **The answer per member,** checked in code:
  - `label`: one of original, new_facts, opinion, same, not_this_story;
  - `facts`: at most 4 per member, each with `span` (5–25 words, which must occur in the member's text), `correction` and `about_story`;
  - `claims`: each with a span;
  - `point`.
- **Final checks** (ported from `final()`):
  - every span occurs;
  - facts with `about_story: false` are dropped;
  - a fact whose quantities all appear earlier in the story is dropped (the repeated-quantities rule);
  - a one-line take becomes `same`.
- **One run in production** (the lab voted over 3). Cost per pass, estimated: about 150 stories × about 8 members over 30 days, about $1–2. Later passes judge only changed stories.

### B4. New task kind `sheet` (guide `persp-merge-v1`, from `persp_merge_v1.md`)
- **One call per story** after its perspectives: the members' facts merged into one deduplicated list, each fact with its sources.
- **The sheet,** ported from `sheet()`:
  - the original or source page;
  - **New facts**, merged, each with its members;
  - **Before the release** (members published before the original);
  - **Unconfirmed claims;**
  - **Opinions**, one line each;
  - **Related**, deduplicated;
  - "N more say the same", folded.

### B5. Storage
- `mx_perspectives` (the same migration): story, post, run, label, facts (jsonb with spans), claims, point, call, `valid_from`/`valid_to`.
- `mx_sheets`: story, run, sheet (jsonb), call, `valid_from`/`valid_to`.
- A change opens a new row and closes the old one; nothing is deleted.

### B6. Shown on the Mark X story view
- **Each member's line** shows its label, a short sign (original ★, new facts +, opinion ~, same =) and its new facts as one line each. Copies are folded.
- **"Worth opening"** = original, new_facts or opinion; the rest is folded under "N say the same".
- **The sheet** sits above the members.
- **The header** reads: **"Experimental: on unseen stories about 83% right on worth opening, 62% on new facts (lab, 2026-11-05)."** These numbers are replaced by the owner's labels once there are 50 of them.

### B7. Label buttons
- **On each member line:** ✓ / ✗ on the label; on ✗, the right label in one tap (original, new facts, opinion, same, not this story).
- **On each new fact:** ✓ / ✗ ("not new" / "not true to the post" / "not about this story").
- Stored in `mx_labels`:
  - new item kinds `perspective` (a = story, b = post) and `fact` (a = story, b = post, `note` = the fact's index and text);
  - `labeller = 'owner'`, `split = 'test'` (they are unseen by construction). **Perspectives have no bar to re-pick:** these labels only report accuracy; nothing is tuned on them. Changing the guide is a new guide id, measured again on new labels.
- **The Labels tab** counts them and shows the running accuracy per label and for new facts, with Wilson intervals, against the lab's numbers.

## The worker
- **New kinds:** `alias` (A1), `perspective` (B3), `sheet` (B4). Each with its guide and JSON schema in `schemas.py`; the worker sends the schema (v10.0.1's `system_for`).
- **The default `--kinds` order** becomes: read, entities, alias, check, join, pair, merge, perspective, sheet, connect, card, headline, briefing, translate.
- **The Worker tab** shows the new kinds' queues.

- **The real-data check** (`scripts/realdata-check.sh`) passes, including `markx.api_during_run` with the new stages, and four new invariants:

  - `markx.entity_redirect_loop`: no redirect chain loops;

- **The reader review** on the real `/markx`:
  - 0115's three complaints are the cases: one list, a click opens every post and source, reading never removes;
