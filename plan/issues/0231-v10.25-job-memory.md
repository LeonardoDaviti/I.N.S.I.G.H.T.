## What changed
1. **`services/page_titles.evidence`**, the one owner of "a page's title by the stored data". Discover's articles,
   origin and archive lines and Classics all use it, in both the Discover job and the story job (`_discover_step`,
   `keep_discover`, `NewsService._classics`).
   - The linking posts' ids come from one query (`StoriesRepository.linking_posts`). They are then loaded
     `LOAD_BATCH` (2,000) at a time, and each post is loaded once.
   - Each post is kept only as the evidence for the pages asked (`_as_evidence`): those pages' links, link words and
     quoted words, plus the first of its other links. That one extra link keeps `origin_title`'s "this link alone"
     test (a share's title) the same as for the whole post.
   - Each page's posts are sorted by (t, id) when they are read. The old code sorted the rows by the same key before
     using them, so the order is the same.
   - `load_posts(linking=…)` is gone (`evidence` was its only caller). `load_posts(ids)` is the one loader.
   - Expected effect, not measured: the 358k-link working set becomes one batch's (~2,000 posts) plus ~18k small
     posts. CPU should be close to the old code's, since no post is loaded twice.
2. **`NewsRepository.load_titles`** returns the rows as they come off the cursor, not a fetchall turned into a list of
   dicts. `NewsService._titled` builds its StoryPosts as it reads them. That removes the tuple list and the dict list
   the names step held next to the StoryPosts (100 → 259 MB before `_titled` on the copy). Not measured after.

The outputs should be identical by construction. The second unit test below checks that every title `origin_title`
gives on the cut-down posts is the one it gives on the whole posts. The DB test checks batches of one against one read.
Not yet shown on real data.
