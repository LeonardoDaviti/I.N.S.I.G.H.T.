# 0239 — v10.26: Discover's cards, platforms, videos, repositories and a reader-fit term (backlog 0237 #2, #5)

## Status: built, tested on invented rows only. NOT measured on real data (owner's order: no real data in v10.26)

## What was wrong
- **A company's card was led by the wrong host.** `one_card_per_domain` led a card by its highest-scoring host. For one
  company that was the investor-relations host (most links); its newsroom host was only a place. The judge reads the
  lead (`source_judge.daily` asks `https://<key>`), judged the IR host `not_fit`, and the card sank to the bottom.
- **One followed newsletter hid a whole platform.** `discover_open` hid every host whose *site* you follow. A newsletter
  platform is not in the Public Suffix List's private section (`site_of` keeps `<name>.<platform>` on the platform's
  site, on purpose: test_reading_gaps, test_voices_and_roundups). So following one publication there hid all others.
  The federation test (`discover_rules.federation`) that knows such sites ran only after that filter, on what was left.
- **Videos counted for no one.** `youtube.com/watch?v=<id>` names no account (`NOT_ACCOUNT`), so a channel's videos were
  an "unnamed" place, never its channel.
- **Repositories were never suggested.** Discover keys GitHub at the owner (`github.com/<org>`, `account_key`), and an
  org whose follow test finds no feed is dropped (`not_channel`). A repository's releases feed was never a row.
- **Ranking is by volume.** Within a section and judgement the order is by `score` (voices, stories, opens). Only 15
  rows a day are judged, so broad outlets lead the ~4,300 unjudged rows.

## What changed (each in the module that owns the decision)
1. **Card lead** (`discover_rules.announcing_place`, `one_card_per_domain`). Inside a card of 2+ hosts, the best-scoring
   place that announces leads: a host label below the site, or the path its follow test found its own pages under
   (`url`, 0172 b7), read by official channels' one rule, `markx/official.ANNOUNCING` (imported, not copied). Else the
   best leads, as before. The card's score is now its best place's (was its lead's). The judge reads the lead's key, so
   it reads the newsroom. Deterministic; ships on.
2. **Platform domains** (`discover_rules.site_unit`, `discover_open(publication_sites=)`, `origins(publication_sites=)`,
   `SourceFacts.followed(publications_on=)`, `StoriesService._publication_sites`, `_held`). The sites of publications
   (SourceFacts.shared_sites + the federations by the data) are found **before** what you follow is read. Federation
   candidates: sites with 2+ suggested hosts, or a followed site with a suggested host. On those sites the unit you
   follow is the publication, for the "followed hides it" rule, the stories' origins, the held places, the card fold
   and the originals rows (`_from_originals`; the answer carries `publication_sites`). `site_of` is unchanged.
   Deterministic; ships on.
3. **YouTube** (`services/discover_reads.read_video`, `videos_due`, `channel_key`; `DiscoverRepository.linked_videos`,
   `video_channels`, `map_videos`; `discover_address(channels=)`; `StoriesService.map_videos`, `_counted(moved=)`).
   Each Discover reads pass reads up to VIDEOS_PER_PASS = 25 linked videos' oEmbed (`author_url`). Videos are read
   most-linked first. Each answer is kept in the existing `discover_reads` setting under `videos`. A channel found is
   never asked again; a failure is asked again after CHECK_DAYS (6 h when transient). A video read is its channel's
   address in `discover_addresses`: updated in place, and a refill under new rules reads the same map. The channels'
   counts are made again through the incremental path, so the usual bar (3+ voices, 2+ article-like) makes a channel
   a row. Stories whose origin is a read video start at the channel. piped/invidious mirrors: **not built**. The
   normaliser does not know them (0225 #33 stays open).
4. **GitHub** (`DiscoverRepository.repos`, `_REPOS`; `StoriesService._repos`). A repository 2+ voices link
   (REPO_MIN_VOICES, the owner's bar) is a row of its own: key `github.com/<o>/<r>`, url its `releases.atom`
   (`official.channel`, the one reading of a repository). Not a row when a source already reads its releases
   (`official._releases_followed`) or you hid it. **Why its own row, not under the owner's card:** the thing followed
   is one feed per repository. An org's card usually leaves (`not_channel`: no feed at the org). One card can follow
   one address, and an org with several linked repositories would hide all but one. The judge and the follow test read
   one address each, and the finder maps a repository to its releases feed directly. Voices are platform_rows'
   (a website's publication, else its source), so a subreddit counts once.
5. **Reader-fit term** (`discover_rules.reader_fit`, `fit_score`, `order(reader=)`;
   `DiscoverRepository.read_sources`). Each row carries `reader_fit`: of the sources linking it (a card: all its
   places'), the share you read in READ_DAYS = 90 (a post opened, read in a session, or marked read). With
   **INSIGHT_DISCOVER_READER_FIT=1 (default off)**, an unjudged row (`fit` None) is ranked by
   `score * (1 + READER_FIT_WEIGHT * reader_fit)`, READER_FIT_WEIGHT = 1.0, **not measured**. No model call. Tracks
   are not used: no per-story track membership is stored cheaply, so that is left until this term is measured.

### What `order()` changes, and for which inputs
- Switch off (default): the same order as v10.25 for every input. The sort key only reads `fit_score`, which is
  `score` when off.
- Switch on: only rows with no judgement (`fit` None) move, and only among rows with the same (judged follow, section,
  FIT_ORDER rank, linked or not). Within that group they sort by `score * (1 + reader_fit)` instead of `score`. Judged
  rows (follow, maybe, skip, not_fit) keep their score. Example (test): broad 5.0 with fit 0.1 (5.5) vs primary 4.0
  with fit 0.6 (6.4): primary goes first.
- Slice C (#3) may change the sections. That change is independent of this one.
