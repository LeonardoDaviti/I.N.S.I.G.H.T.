# 0177 — The server's remaining load (v10.16 slice M)

Status: **built** (branch `v1016-load` from main 784d232). Not merged, not pushed, not deployed. Migration **0120**.

## The problem (the server, v10.15.1, 2026-11-12)

An incremental decision run took 173 s: entities 73.5 s, questions and decisions 24.6, back 25.2, graph 9.4,
perspectives 9.4, news 7.4, surges 5.3. The plan job's track pass took 36 s each time, cite 15.7 s.
`/api/markx/overview` 4.4 s, `/api/markx/entities` 5.0 s; insight-api ~2.3 GB RSS on average, 3.2 GB at most.

## How it was measured

A server-sized scratch copy (148k posts, 1.08M tasks, 966k calls, 830k mentions, 130k vectors, 4 tracks with 56k
judged items), its Mark X rows made by the real decision runs over a synthetic worker's answers; then "an hour of
ingestion" (300 new posts, edits, pages stored at linked addresses, a Mark IX surge). Before (main) and after on the
same snapshot, each scenario in a rolled-back transaction: per stage seconds, peak RSS, bytes from the database, and
a digest of every Mark X row it wrote. Numbers in plan/research/load-v1016.md (private).

**Equivalence.** Every row the decision run writes, the track planner writes, and the two API answers are identical
before and after. Two places where main's own result varies run to run were found and held fixed to compare (not
changed): identity's capped alias questions are chosen in hash order (PYTHONHASHSEED), and the entity list's third
story of a row is a tie taken in fetch order.

## What was built

1. **Entity book.** `decide.run` reads the whole book once for the entities stage (`entity_stage.entities(book=)`)
   and once more without the mention counts for the surges and the perspectives, which never read them (was: a whole
   book each, three a run). The entities stage's own time was the handle rule's scan (0168): its "Name (@handle)" pair
   pattern tried 80 characters from every position of every post's full text; a text without "(@" holds neither a
   pair nor an embed and is no longer searched (10x on the scan). Copy: entities 38.7 -> 14.3 s, surges 1.5 -> 0.2 s.
2. **Track planner.** `finders.learn`'s window counts (entities, link sites, words, posts and terms) are read once a
   pass for every track (`finders.prefetch`, a cache keyed by the window), window-first, the words by Postgres' own
   document counts (`ts_stat`); the judged posts once a track (they were read again for each label the classifier's
   leave-one-out leaves out, every post of the sources probing the items). A classifier training whose labels lack
   vectors for 8 of each is known by one query: it stored no model and was retrained every pass. Copy: 7.8 -> 2.7 s a
   pass; with the classifier 54 -> 16 s. A stored model is still reused until 10 new labels (unchanged).
3. **back and graph.** back's trigger computed the earliest window of every story again for each recent post (3.5M
   calls) and normalised the same addresses many times: once, and kept per address. Copy: back 19.3 -> 15.3 s. Graph's
   stage is bound by its clock already; what it costs is discover's same-subject cosines (below).
4. **News incremental under ingestion.** The run's state keeps, for each post News reads, a digest of its text stamp
   (row, parts, links rows) and of its links' resolution, the source facts as a StoryPost reads them, and Mark IX's
   surges. The posts whose digest changed and those of a changed surge seed the rows made again (0116's closure);
   changed facts make News in full. Copy: 1.62 -> 1.05 s; the rows identical, and a full run of that snapshot finds
   its incremental reading the same (`check: same`). News sections (0174) read the same rows.
5. **The API.** Migration 0120: indexes answering the overview's queue counts, failed tasks, token totals and last
   invalid calls (they were sequential scans of ~2 GB of tasks on the server): 373k -> 15k pages read, 0.45 -> 0.2 s on
   the copy. `/entities` reads the merges, the pins and only the entities its rows name, then their makers' and
   families' (`identity.read_ents`), not the whole book: 0.85 -> 0.45 s on the copy (70k entities; the server's 250k
   weighed more).
6. **insight-api memory (reported, not changed).** The Labels tab's queue (`labels.population`) is a whole decision
   reading inside the API process: on the copy a 2.4 GB peak of Python allocations, RSS 3.4 GB after, 1.5 GB after
   `malloc_trim`. It is cached once per decision run (one queue: bounded, not an unbounded cache) and rebuilt on the
   first open after each run, so the API's RSS sits at the last build's high-water mark. Discover's background build
   peaked at 0.2 GB on the copy. Options for the owner: build the queue in the jobs process after a run and keep it;
   `malloc_trim` after the build; `MALLOC_ARENA_MAX=2` for insight-api.
