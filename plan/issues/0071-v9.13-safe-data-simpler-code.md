## A. Your data can't be lost by a file
1. **The database is the truth for sources; `sources.json` is an export.**
   - **Today:** both containers mirror the file into the database at every start, and daily. A source missing from the file is deleted with its posts (up to 83 of 247 without warning). The file is in git, and the API rewrites it without a safe write.
   - **Decided:**
     - Adding, editing and removing a source write the database only. Removing happens only through Remove in the UI, as now.
     - The file is written as a backup export after each change: written to a temporary file, then renamed.
     - Importing a file (first install, or by hand) only adds and updates, and never deletes.
     - The file leaves git: untracked and gitignored, with an example file kept for new installs.
     - A missing, empty or broken file changes nothing.
   - **The server's deploy:** the server's file has local changes from the UI, so a pull that deletes the tracked file would refuse. `DEPLOYMENT.md` gets the steps: set it aside, pull, put it back, and the new code reads it once as an add-only import.
   - **Done when:**
     - tests: a file missing sources deletes nothing; a broken file changes nothing; an import adds; the export is atomic;
     - a dry run on a copy of the server data: 0 sources deleted, 247 kept.
2. **A start never fails for something non-fatal.**
   - A bad source entry, or two containers adding the same source, is logged and skipped.
   - `/health` makes one quick database query.
   - `update` lists the migrations it will run before running them.
3. **The API answers only the machine it runs on** (127.0.0.1 in compose), with the frontend's nginx reaching it on the compose network.
   - Check first that the owner's way in (`http://<serverip>:5173`) goes through nginx only. If anything calls the API port directly, record it and stop.
4. **One API worker, enforced:** the start refuses `--workers` > 1, with a message saying why. The architecture review lists six things that break with two.

   - **Measure** which way catches both past misses (0068's `site_of`, 0068's titles) without a full rebuild after a refactor that changes nothing:

   - Adopt the one that does, record why, and remove the hand constants.
   - **Done when:** tests show that changing a rule's output changes its stamp, and a pure rename doesn't (under the adopted way). The stale 1,769 Discover rows refill on the lab copy.

### A1. The database is the truth; sources.json is an export
- **Built:**
  - Adding, editing, removing and switching a source write the database; the file is rewritten after, to a temporary file renamed over it (`export_db_to_json`). The main-digest switches (a source's, a track's) now export too.
  - `import_json` only adds sources and sets their on/off; it never deletes. A missing, empty or broken file, or one without `platforms`, changes nothing; a bad entry is skipped and logged.
  - A start imports once per database (`system_settings.sources_json_imported`): a new install, or the first start after this deploy. Later starts don't read the file, so a stale file can't bring back a removed source. By hand, any time: `sync_sources_json.py json-to-db`.
  - Gone: the mirror-delete, its 34% guard, `INSIGHT_ALLOW_BULK_SOURCE_DELETE`, the daily sync and its switch (`INSIGHT_SYNC_SOURCES_EACH_CYCLE`, the Scheduler dialog's "Sync sources.json every cycle"). A switch whose export fails now stands; it was undone.
  - The file left git (`git rm --cached`, gitignored, kept out of the image); `sources.example.json` uses neutral addresses. `DEPLOYMENT.md` has the server's pull steps: move the file aside (the running code refuses to mirror a missing file), pull, put it back, update.
- **Dry run** on `insight_0071a_server`, a copy of `insight_server_copy` (239 sources, 41,608 posts; the server copy holds 239, not the lab's 247). Each case was a full start of the new API (migrations, the import, `/health`):

  | sources.json | import | sources after | deleted |
  |---|---|---|---|
  | missing (first start: 0038-0053 ran) | nothing, start goes on | 239 | 0 |
  | cut short at 5,000 bytes | "could not be read", start goes on | 239 | 0 |
  | the database's own export (as the server's file is) | added 0, updated 0 | 239 | 0 |
  | the export less 80 sources | added 0, updated 0 | 239 | 0 |
  | the repo's committed file (7 sources missing, 3 extra) | added 3, updated 2 | 242 | 0 |
  | the same file, a later start (the ingestion container's) | "imported before" | 242 | 0 |

  Posts stayed 41,497 after the migrations in every case (0038 and 0052 merge copies). The old code with the repo's file would have mirror-deleted those 7 sources and their 393 posts.
- **Wrong, or worth knowing:** an add-only import of a stale file still adds the sources the owner removed and flips on/off where the file differs: the repo's old file on the server copy added 3 and flipped 2. That is why the server must put back its own file, as `DEPLOYMENT.md` says. The fix is not to import that file; deciding whether an import should set on/off at all is the owner's (the spec says it updates).

### A2. A start never fails for something non-fatal
- **Built:** both start scripts go on when the import fails (a missing or broken file, a bad entry, a source the other container added meanwhile: "already a source" is skipped). Migrations stay fatal. `/health` runs `SELECT 1` through the pool and answers 503 when the database doesn't. `./update` prints the pending migrations (`migrate.py --pending`, read-only, each with its header's first line) before `up -d`; on the server copy it listed 0038-0053 (13).
- **Worth knowing:** with the database down, a pooled connection waits 10 s (`INSIGHT_DB_POOL_TIMEOUT_SECONDS`), as long as the healthcheck's timeout, so the check fails by timing out rather than by the 503. Unhealthy either way.

### A3. The API answers only the machine it runs on
- **The check first:** nothing in the repo calls the API's port from outside. The app calls `/api` on its own origin (`lib/request.ts`, `lib/mediaProxy.ts`) unless `VITE_API_URL` is set at build; nginx proxies `/api` and `/api/media` to `backend:8000` on the compose network; the bookmarklet opens the app's own `/save`. A browser at `http://<serverip>:5173` calling `:8000` directly would also need `CORS_ALLOW_ORIGINS`, since the default origins are `localhost` only. If `:5173` is Vite's dev server rather than nginx, it proxies to `localhost:8000`, which `127.0.0.1` still serves.
- **Not checked, so not claimed:** the server's own `.env` (this machine can't read it). The pull steps start with `grep -c '^VITE_API_URL=.' .env`, which must print 0, and stop otherwise. A tool on another machine calling `:8000` would lose it; the way in from elsewhere is an SSH tunnel.
- **Built:** `127.0.0.1:${BACKEND_PORT}:8000` in compose; DEPLOYMENT and README say so.
