# 0235 — v10.25: a voice the owner wanted was found by Discover and buried (backlog 0225 #32)

## Status: built, tested on synthetic rows only. NOT measured on real data (owner's order: no real data in this slice)

## What was wrong
- **Nothing judged her.** The source judge (0173) asks only on the owner's tap. The automatic check
  (official.check_suggestions, 10 a day in the official pass) looked only at the **first 300 rows** of Discover's
  order. That order is by link volume, and her row was far below row 300 of 4,349.
- **A judgement could not lift her anyway.** Discover's served answer is cut into pages in Postgres (0206
  `served_window`), and `_by_fit` re-ordered only the page's 30 rows. So a row at #4,000 judged "follow" never reached
  page one. Inside the order, fit came after the follow-test section. Rows only get a follow test once they are on
  the first page, so an untested row judged "follow" still sat behind every tested one.
- **The score has no growth.** ln(1+sources) plus a flat recency bonus. Six new sources in two months score below an
  outlet that 59 sources have linked for years.
- **A healthy track is never scouted.** `scout.due_weekly` only picked tracks with fewer than 5 items in 7 days.
- **A mention counts nothing.** Matt Pocock wrote ".@poteto's talk" with no link. Nitter renders the mention as a link
  to its own profile page, and extract_links drops those as "the platform's own". So no row was written at all.

## What changed (each in the module that owns the decision)
1. **Daily judgement** (`markx/source_judge.daily`, `to_judge`). This moved from `official.check_suggestions` /
   `to_check`, which are removed, so there is one path. Up to JUDGE_DAILY = 15 Discover suggestions a day, JUDGE_PASS = 5
   per official pass (every 30 min). It skips any key judged within CACHE_DAYS and any row whose follow test says it
   can't be followed. Rows are picked by `growth`, highest first, then by score. Each pick goes through `ask` +
   `read_and_ask`, the same path as a tap, at DAILY_PRIORITY -2. A tap is -5, so a tap still comes first. The day's
   count is read from `mx_source_judgements.asked_by = 'daily'` (migration 0160). It runs inside the jobs process's
   existing "official" job (official.run), so it needs INSIGHT_OFFICIAL not off (the default is shadow). jobs.py is
   unchanged.
2. **Growth** (`discover_rules.growth`, `score(grown=)`). The term is share_new × ln(1+new), where "new" means sources
   whose first link to the key falls in the last GROWTH_DAYS = 30. It is weighted GROWTH_WEIGHT = 1.5. **The weight is
   not measured yet** (this is said in a comment). It is computed in the existing activity query
   (`repo_discover._ACTIVITY`, now grouped by key and source in the same pass), so there is no extra table scan. Each
   suggestion carries `growth`.
3. **The order** (`discover_rules.order`, `judged_follow`; `StoriesService._fresh`). A row the worker judged "follow"
   now goes before every section, unless its follow test says it can't be followed as a feed. Fit is applied to the
   whole answer when it is built, not only to the page being read.
4. **Weekly scout for every track** (`scout.due_weekly`). Every described track is due once a week, with starving
   tracks first and then the track unscouted longest. One weekly run starts per tick, and none starts while another
   weekly run from the last week is open, so the runs follow each other. MAX_READS and the budgets are unchanged. The
   match finder now reads mentions too.
5. **@mentions are links** (`utils/post_links.mentions`, `extract_links(..., content)`). For X posts (kind x) and
   Bluesky posts (by address; read from the plain text, since they have no HTML), an @handle in the text becomes a
   link row of kind `mention` to `x.com/<handle>` or `bsky.app/profile/<handle>`. These are skipped:
   - the reply's leading run of @handles;
   - the post author's own handle;
   - an @ inside an address or an email (only an opening mark may stand before it in its word, so `.@name` counts);
   - a handle that runs on into more characters, a domain or a second @.
   A mention row is stored as **boilerplate**, as a reference is. So no story, News, Classics or Mark X rule reads it,
   and the signature pass keeps it boilerplate. Discover (`repo_discover.read_sql`), the scout's match finder and the
   judge's `linked` signal read kind = 'mention'. Mark X units' skip list and source_stats leave mentions out, so a
   post's split does not change.
6. **Discover's counting of an account mention.** The key is the account (x.com/<h>; Bluesky is now a platform:
   PLATFORM_SITES "bluesky", account_key reads bsky.app/profile/<h>, and a Bluesky post is one of its account's
   articles). A key that posts @mention needs no article-like pages, only DISCOVER_MIN_VOICES (3) voices, counted from
   mentions and links together (the SQL candidate rule and the reference `suggestions(mentioned=)`).
7. **Backfill, resumable, not run.** `StoriesRepository.fill_mentions` and `scripts/backfill_mentions.py`. It reads the
   posts of X and Bluesky sources whose text holds an @, by id, in batches of 500. Its place is kept in system_settings
   `mentions_backfill`. Each post's links are rewritten as they are read now (the same rows plus the mentions). At the
   end it drops Discover's kept counts so the next count is a full one. No job runs it: run it by hand after the
   deploy.

## Measured (synthetic only)
- Backfill: 20,000 synthetic X posts (5 handles each, 3 kept as mentions) took **82 s (4.1 ms a post), peak 75.5 MB**,
  and wrote 60,000 mention rows. Per-post `write_links` dominates. Cost on the server: about 4 ms × (X/Bluesky posts
  with an @). Not counted on real data.
- Not measured: Discover's count time and peak with the `mention_url` CTE and the per-source activity query, on
  server-shaped data. The address-rules stamp changes (Bluesky samples were added), so the first count after the deploy
  re-fills every `discover_addresses` row once. The `_COUNTS` text changes too, so that first count is a full one.

## Daily cost
- Judge: at most 15 `source_judge` Haiku calls a day, and 15 test reads (each up to ITEMS = 10 items, plus up to
  PAGE_CHECKS = 2 page reads for a teaser feed). Before: at most 10.
- Scout: each described track once a week. Per run: up to MAX_READS = 40 test reads, MAX_JUDGEMENTS = 800 `track`
  Haiku calls and 1 `scout` call. For N tracks that is ≤ N × 800 / 7 ≈ 114·N Haiku calls a day at most. Runs are one
  at a time. The number of tracks on the server was not looked up.

## Risks
- **First page taken over by judged rows.** Up to 15 judgements a day, and every "follow" goes before every section.
  Over 30 days the first page could be all judged rows. That is intended (the worker's pick over link volume), but it
  has not been looked at on real data.
- **INSIGHT_OFFICIAL=off also stops the daily judge** (the same pass carries it).
- **First count after the deploy is full.** The address stamp and the counts query changed, so it re-fills every
  discover_addresses row once. Time and peak are unmeasured.
- **Bluesky keying changed.** Links to bsky.app posts or profiles, which used to be one site key "bsky.app", are now
  per account. A followed Bluesky source's account is now bsky.app/profile/<h> (account_key), so it is recognised as
  followed. Its follow test still goes the generic way: discover_reads.kind_source has no Bluesky branch.
- **Mentions skip the signature rule.** A source that mentions the same co-host in every post counts as a voice for
  that account. That is only one voice; 3 are needed.
- **Quoted text counts for the quoting voice.** The mentions inside a Nitter quote's text are credited to the quoting
  post's voice, as links are.
- **Scout cost grows.** Every track now runs weekly, not only starving ones. The cost is bounded per run, not per day.
