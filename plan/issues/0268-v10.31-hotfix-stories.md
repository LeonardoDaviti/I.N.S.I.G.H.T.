# 0268 — v10.31.1 hotfix: stored stories re-dated by a new dating rule; a release row named by its release

Status: **built** (v10.31.1, not deployed). Cases: `stored-story-dates-not-backfilled`,
`fable-5-2-release-row-headlined-by-physics` (plan/research/lab/cases.json; the real rows belong in
plan/research/v1031/, not here).

## 1. A dating rule change re-dates the stories already stored

**Bug.** 0263's rule (a Saved page more than 72 h before its story's first report never dates it) is applied where a
story is written: Mark X's `decide.persist` (only the stories the run reads: its window) and Mark IX's grouping (only
on a regroup). Nothing re-dated the stories stored before: Mark X's are re-dated only when they are in a run's window
again; Mark IX's never, because Mark IX's rules stamp (utils/stamps.py, 0071) is a fingerprint of what the rules make
of a fixed sample, and the sample had no Saved page older than its citers by 72 h, so 0263 kept the stamp and no
regroup came.

Note on production (2026-11-21): the last Mark X run read before this fix (93435721, 11:51-11:53 UTC) began before
the v10.31 deploy (commit 11:57 UTC), so the in-window case of the bug (a release story of 2026-11-20, still dated by
its Saved paper) is re-dated by the first run on v10.31 already; the fix is for every story outside the window and for
Mark IX's.

**Fix (in the modules that own the rule's stamp, no parallel path).**
- Mark IX: the stamps sample gets 0263's case (`n4`-`n6`: a Saved page two months before the two voices citing it).
  The `grouping` part of `rules_stamp` changes, so the story job regroups every post once by the current rules, as on
  every rule change since 0071 (bounded steps; StoriesService.step). `test_stamps` proves the part sees the rule
  (patched off, it changes) and that the sample's story starts at its first report.
- Mark X: the dating rule is stamped the same way: `decide.dates_stamp()` is a fingerprint of what `_start` makes of
  `stamps.story_dates()` (cases at each edge: 60 days, exactly 72 h, 72 h 1 min, a voiced leak 4 days early, Saved
  pages alone). A run that finds another stamp than the one kept (mx_settings `story_dates_rule`) re-dates every
  current story once (`decide.redate`: one read of the current rows, `_start` over each story's current rows as
  `persist` dates a story, an UPDATE only where the date moves) and keeps the stamp; counts `redated`. Idempotent; a
  merged-away story is left as it is.
- News follows by itself: Mark X's News rows are made from the posts (`rows_of`: story_times, background), never from
  the stored first_at, and the code stamps changed in v10.31, so the first run makes News in full.

**Cost.** Warm on the 11-05 server copy: the read is 31 ms for 1,200 current rows of 344 stories; at today's 3.6k
stories (about 10x), about 0.3 s plus a Python pass, once. The copy of 11-19 measured 4 Mark X stories (6 Mark IX)
whose date moves. Mark IX's regroup is a whole regroup (measured 6.2 s per 1,000 posts in 0071's steps).

## 2. A release row is named by its release, never by a result merged into it

**Bug.** A model release's row (131 posts, 35 voices, 24 Mark X stories) was headlined by the maker's research result
announced the same day (6 of its posts). The row is a one-release row (0236: chains.one_row on; a same_release chain
edge joins stories into one row), so its headline is `news.launch_order`'s first: "the maker's stories, the newest
first". The newest maker story with a headline was the result (released 45 minutes after the launch), not the launch.

**Fix (`news.launch_order`).** In each tier (the maker's stories, then the others of a news type): a release first
(utils/grouping.RELEASES), then the story holding most of the row's voices (`weight`: `story_voices(row)`, the
main_story count), then the newest (as before). Teaser -> preview -> launch still names the launch (leaks never name a
row; of two release stories the one most of the row's voices are in, then the newest). Tests: the maker's result and
its Q&A never name the release; a DB row of a launch story and a newer maker result story joined by a same_release
edge is named by the launch.

**Should the result be in the release row at all?** No, by the owner's rule (one release of one thing is one row; a
maker's later Q&A belongs in it; a separate result is a separate event). The story layer already keeps it apart (its
own Mark X story, 6 posts: the maker's post, its relays, the maker's page a week later and its HN post); the row
joins it by 0236's same_release edge (rule chain_stops: two stops of one thing, the later asked how they relate,
both runs agreeing) — the stored edge (mx_connections, its `evidence`) is not readable by GET and the server copy was
being restored; read it there. The row also holds 8 posts of no Mark X story joined by the surging name. Left: the
same_release question should answer "a result shown with the thing" as no release stop (measure on 0219's held-out
sets before changing the guide); until then the headline fix keeps the row named by the release.
